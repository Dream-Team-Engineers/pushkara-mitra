## Observed accounts and roles: do not invent parity requirements

The reference provides public browsing without signing in. Google identity is observed for pilgrim registration and identity/contact verification. Client profile state is remembered locally; this is not proof of a secure backend session. Native sign-in and image-save hooks are present but the actual native wrapper is not in the inspected browser source.

Groups use a member name and join code in the observed client; Google sign-in is not enforced by that client flow. Lost/found submission itself is not observed to require Google sign-in, while requesting contact access does. Public notifications are distinct from verification updates for a signed-in person.

Report approval and verification decisions imply some external operator process, but no in-app admin console, moderator login, permission matrix, server role model or Apps Script implementation was found. Do not label an admin portal or RBAC hierarchy as copied/reference-proven. Pushkara still needs an original approved staff authorization model for safe publishing/moderation, separate from actual observed pilgrim flows. Admin Access-only authentication cannot replace pilgrim authentication where full parity requires signed-in registration/status/access flows; conversely, do not require accounts for all public browsing just because protected actions need identity.

## Proposed technical choices for the full target

The coordinator selects this implementation direction in response to the user's request to decide for full parity. These are concrete proposed contracts for review, not permission to process real personal data or bypass G0/G1:

- Public information remains browsable without an account. Protected pilgrim workflows use Google OIDC sign-in, matching the observed reference provider, with server-side verification and secure revocable sessions. Client-decoded claims or phone-entry widgets are not authority. Provider configuration and approved identity/session lifetimes remain operational/security prerequisites.
- Staff administration uses separate Cloudflare Access verification and server-side permissions. Administrative identity is not inferred from a public Google profile or reference-side verification badge. Moderation and publishing permissions are reviewed per operation.
- Keep the existing Cloudflare Worker, D1 for approved minimal durable records and Durable Objects for approved ephemeral-only location. No coordinate or movement persistence, even if the reference's remote service might retain it.
- Preserve all observed screen/flow acceptance items. Deliver in dependency order rather than delete items from scope. Telugu is default; Hindi, English and Marathi retain reference language coverage with human-reviewed translations.
- Use original implementation and properly sourced assets while reuse permission is unknown. Real provider configuration, reviewed Godavari data, abuse/moderation operations, retention and notice decisions are explicit prerequisites; do not substitute mock success for working integrations.
