# 0019. Partners (priests and volunteers), phase 2 of the staff dashboard

Status: Proposed. Design and threat model for the staging build only (owner decisions 2026-11-23, ADR 0018 section 7). Production stays off until the owner approves the release; counsel review is recorded with the counsel details (OQ-024), still pending. Nothing in this ADR is legal advice or a compliance claim.
Date: 2026-11-24

## Context

Priests and volunteers can help pilgrims by reporting what they see (crowd level, river level, free food) and by answering requests from the staff. The owner chose: partners sign in with Google and ask to join; one of the three admins approves; approved partners switch themselves available or not; admins nudge partners through an in-app inbox (phone notifications come in phase 3); partner updates reach pilgrims at once, marked "from a volunteer", and admins can hide one.

The risks are different from groups. A false crowd or river report can send people into danger or cause panic; a fake "priest" can gain trust; the admin dashboard, read-only until now, gets its first write actions; and vetting a person needs a name and an email that the rest of the app never stores (DI-14). Location is not needed and is never collected from partners (Hard Rule 1).

## Decision

1. **Apply.** A signed-in person (Google, staging) opens Partners and taps "I am a priest" or "I am a volunteer" (fixed choices, no free text), optionally picks a home ghat from the fixed ghat list, and ticks a separate partner consent line (purpose `partner`, notice version `partner-1`, recorded through the consent ledger). The application stores the person's pseudonym, role, ghat, and the first name and email from their Google sign-in, so that an admin can recognise them. The session cookie never holds the email (DI-14), so the apply step sends a fresh Google sign-in token (with the nonce from this browser's cookie); the server verifies it, checks it belongs to the signed-in account, and takes the name and email from the token, never from what the page says (owner decision 2026-11-24). Name and email are kept only for applicants and partners, are shown only to admins, and are never shown to pilgrims or other partners (DI-20).
2. **Approve (admin write, narrow).** The admin Worker gains exactly three write actions, each behind Access and the existing token check, each a POST with a same-origin check and a CSRF token: approve, reject or suspend a partner; send a nudge; hide or unhide a partner update. It still never lists pilgrims, groups, positions or group names. Every decision records which admin (the Access subject, not an email) and when (`partner_audit`, DI-22). A rejected application's name and email are deleted after 30 days; the pseudonym and the decision stay so a rejected person cannot reapply in a loop (one application per 30 days).
3. **Availability.** An approved partner has one switch: available or not. It starts off and switches itself off after 12 hours, so a forgotten switch does not make the app claim help that is gone. Pilgrims never see who is available; only the admin Worker sees counts, so nobody can be targeted by availability.
4. **Nudges.** An admin picks a kind (`crowd`, `river`, `food`), optionally a ghat, and sends it to available approved partners (all, or those whose home ghat matches). Fixed wording only, chosen from the list, no free text, so the inbox cannot be used to send arbitrary messages or links. Partners see their own inbox in the app (unread count on the Partners tab); a nudge expires after 6 hours and is deleted after 24. Rate limit: 10 nudges per admin per hour.
5. **Partner updates.** An approved, currently available partner can post a fixed-choice update: `crowd` (low, moderate, high), `river` (normal, rising, high) or `food` (available, finished) for one ghat from the fixed list. No free text, no photo, no contact detail, no price, no link. Pilgrims see the latest unhidden update per kind and ghat, **only while it is under 3 hours old**, with the label "From a volunteer" and the age, and a line that it is not an official figure. Partner updates are kept in a separate table and are shown beside, never in place of, the official crowd reading (`crowd_reading`); where both exist the screen shows both. River updates carry an extra fixed line that the official flood and river bulletin governs (wording NEEDS REVIEW, OQ-045). Rate limit: one update per kind and ghat per partner per 10 minutes, 30 per partner per day.
6. **Hide.** An admin can hide an update with one tap; hidden updates stop showing at once and are deleted after 24 hours. Three hidden updates for one partner suspend them automatically until an admin reviews.
7. **No location, no tracking.** Partners are never asked for position; no partner location can exist in any table. No partner list is public. Partner identity stays a pseudonym in pilgrim-facing responses (the update carries only the label and age).
8. **Kill switches.** Worker variable `FLAG_PARTNERS` must be exactly `enabled` for any partner route (apply, availability, inbox, update, and the pilgrim read of updates); the frontend `partners` flag is on only in the staging build. The admin Worker's write actions refuse when `FLAG_PARTNERS` is not enabled.
9. **Changing role (added 2026-11-26, owner request).** An approved or pending partner can send a new request for a different role (priest, vendor, moderator or volunteer) or home ghat from the Partners screen. It goes back to `pending` for staff approval, and availability is cleared at once, so a role is never held without approval. The same role and ghat again is refused (`ALREADY_APPLIED`), and a suspended or rejected person cannot use it to get round a decision. The Me tab links to Partners / Volunteers.
10. **Erasure.** "Delete my account and data" removes the person's application, profile, inbox and updates and replaces their audit rows' subject with a removal marker (audit rows keep the admin's decision, not the person).

## Threat model

| Threat                                                    | Mitigation in this design                                                                                                                                                             | Still open                                                                 |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Someone claims to be a priest or officer to gain trust    | Approval by an admin who sees name and email; label is only "From a volunteer", never "priest" or "official"; no free text, links or contact details                                  | How an admin verifies a real priest (owner process); badge wording         |
| False crowd report causes panic, or hides a real crush    | Fixed values; shown with age and "not an official figure"; expires after 3 hours; shown beside the official reading; hide in one tap; automatic suspension after three hidden updates | Counsel view on liability for volunteer reports (OQ-045)                   |
| False river report endangers life                         | Extra fixed official-bulletin line on river updates; short expiry; admin hide                                                                                                         | Whether river updates should wait for an official source; wording (OQ-045) |
| A partner is coerced or spoofed by another user           | Sign-in required; updates tied to the signed-in pseudonym; same-origin check; rate limits                                                                                             | Account takeover on Google's side is out of our control                    |
| Admin account compromised                                 | Access in front of the whole admin Worker; token verified on every request; write actions need same-origin and CSRF token; audit rows; only three admins; narrow write set            | Admin two-step approval for suspension is not built                        |
| Applicant name and email leak                             | Stored only for applicants and partners; shown only on the admin Worker; never in logs, errors or pilgrim responses; deleted 30 days after a rejection; deleted on erasure            | Retention for approved partners after the event (OQ-046); counsel          |
| Partners are targeted for harassment through availability | Availability is seen only as counts by admins; no public partner list; pseudonym only in public data                                                                                  | —                                                                          |
| Spam, scams (fake free food, donation links)              | No free text, links or contact details anywhere; fixed choices only; rate limits; admin hide                                                                                          | Real food-camp verification is a process question                          |
| Nudges used to push arbitrary content to partners         | Fixed wording; only admins can send; rate limit                                                                                                                                       | Phase 3 push needs its own review                                          |
| Partner location appears through this feature             | None collected; guard tests for location stay in force; no coordinate field in any new table or log call                                                                              | —                                                                          |
| Minors apply                                              | Same age and consent rules as sign-in (OQ-030); an under-18 option is not offered for partners                                                                                        | Counsel decision on age for partners                                       |
| Pilgrim data exposed through the admin write routes       | Admin Worker lists only partner records and updates; guard test checks the admin code never reads membership, positions, group names or sessions beyond counts                        | —                                                                          |

## Consequences

- New migration (expand-only) after 0006: tables `partner` (application, profile and availability), `partner_inbox`, `partner_update`, `partner_audit`; `consent_ledger.purpose_id` gains `partner` (SQLite cannot change a CHECK in place, so that table is rebuilt in the same migration, keeping rows and the append-only trigger). Applied to staging D1 by hand before the push, as for 0004 to 0006.
- `tests/guards`: the admin Worker's write set is limited to the three actions; admin code stays unable to read pilgrim tables beyond the existing counts; no coordinates in the new tables.
- ADR 0018 section 7 phase 2 is now this ADR; the admin Worker is no longer read-only once phase 2 lands (ADR 0018 section 3 to be amended in the same change).
- Data inventory DI-20 to DI-23 added. The privacy notice must describe partner data before production (OQ-029).
- Build order: (1) migration and repository; (2) apply, availability and inbox routes with tests; (3) admin Partners tab (approve, nudge, hide); (4) Partners screen in the app and pilgrim "from a volunteer" strip; (5) strings in en, te, hi (te and hi added to the O1 review list).
