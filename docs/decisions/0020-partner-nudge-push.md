# 0020. Phone notifications for partner nudges (Web Push), phase 3 of the staff dashboard

Status: Proposed. Design and threat model only. **No code, migration or secret is created until the owner approves this ADR.** Production stays off until the owner approves the release; counsel review is pending (OQ-024). Nothing here is legal advice or a compliance claim.
Date: 2026-11-28

## Context

ADR 0018 section 7 phase 3 and ADR 0019 section 4: admins already nudge available, approved partners through an in-app inbox (built; fixed wording, 6 hours open, 10 nudges per admin per hour). The owner chose to add phone notifications as well as the inbox. A partner who has the app closed does not see the inbox, so a nudge can arrive too late to be useful.

Web Push is the only phone notification route that needs no native app and no paid service. It brings new risks: a device address held by us that points at a third party's server, a new secret (the VAPID private key), a new sender, and a message that appears on a lock screen.

## Decision

1. **Opt-in on top of approval.** Only an approved partner sees "Get phone notifications" on the Partners screen. It is off by default, needs its own tap (the browser permission prompt is shown only after that tap, never on page load), and records its own consent line (purpose `partner_push`, notice `partner-push-1`, through the consent ledger). Refusing changes nothing else about being a partner. A switch turns it off again at any time; that deletes the subscription at once.
2. **Empty pushes, fixed text.** The push carries no payload. The service worker shows one fixed notification (title "Pushkara Mitra", one short fixed body in English, Telugu and Hindi: "A new request is waiting"; wording NEEDS REVIEW, OQ-048). It never names a ghat, a kind, a person or a place, and carries no link parameters. Tapping it opens the Partners screen, which fetches the real inbox with the person's normal session. This avoids message encryption (RFC 8291), keeps any content off the lock screen, and means a leaked or forged push can say nothing.
3. **What is stored.** Per subscription: the partner's pseudonym, the push endpoint URL and the two browser keys, created time, last-success time. Nothing else: no device model, no IP address, no user-agent, no location (Hard Rule 1). The endpoint is a private address that identifies a browser at Google, Apple or Mozilla, so it is treated like a credential: never logged, never returned by any API after it is saved, never shown on the admin Worker, never in an error message.
4. **Who sends.** The admin Worker sends the pushes, in the same request that records the nudge, after the database write has succeeded. The VAPID private key is a secret of the admin Worker only (the public Worker never holds it). The admin Worker reads subscription rows only for partners who are approved, available and match the nudge's ghat, and uses them only to send. Admin pages never display endpoints. All reads and writes stay in `src/db/adminPartners.ts` and the partner tables, as ADR 0018 section 3 requires, and the guard test is extended to cover the new table.
5. **Best effort, inbox is the record.** Delivery is never promised or shown as delivered. If a push fails, the nudge still sits in the inbox. A 404 or 410 answer from a push service deletes that subscription. Other failures are counted (a number, no endpoint) and shown to the admin as "sent to N, failed M".
6. **Limits.** Each partner gets at most 3 pushes per hour and 10 per day, counted from the nudge table (an extra nudge still reaches the inbox, silently). The existing limit of 10 nudges per admin per hour stays. One push per nudge per subscription, no retries beyond one.
7. **Cap per nudge.** The Workers free plan allows 50 outbound requests per invocation, and the paid-plan decision is open (OQ-028). The send is therefore capped at 40 subscriptions per nudge on the free plan, and the admin sees "sent to 40 of 63; the rest are in their inbox". The cap is a configuration value, raised only when the plan is decided.
8. **Who may be notified.** Only partners. Pilgrims receive no push in this ADR (the multi-channel SOS design is ADR 0015 and separate). A suspended, rejected or removed partner has the subscription deleted in the same step as the status change.
9. **Lifetime.** A subscription is deleted when: the person turns it off; the partner is suspended, rejected or erased (ADR 0019 section 10); the push service reports it gone; it has had no successful send and no re-confirmation for 30 days after an unsuccessful one; or the daily sweep runs on 14 July 2028 (`src/retention.ts`, with the partner data). The re-confirmation is the partner opening Partners while signed in, which refreshes the browser's subscription.
10. **Kill switches.** `FLAG_PARTNERS` must be `enabled` (as now) and a new `FLAG_PARTNER_PUSH` must be exactly `enabled` on both Workers for any push route or send. The frontend `partnerPush` flag is on only in the staging build. With either off, nothing is sent and the opt-in is hidden.
11. **Platform limits (to verify before relying on it).** iPhone and iPad deliver Web Push only to an app added to the Home Screen, on a recent iOS; some Android battery modes delay pushes. Partners who cannot receive pushes keep the inbox. These behaviours are unverified by the agent and must be tested on real phones in staging.
12. **Service worker.** `public/sw.js` gains a `push` handler (shows the fixed notification) and a `notificationclick` handler (opens `/` at the Partners screen). It must keep the existing cache rules: no authenticated or personal response is cached, and the push code makes no network request of its own. CSP already allows `worker-src 'self'`; no new origin is added to `connect-src` because the browser, not the page, talks to the push service.

## Threat model

| Threat                                                            | Mitigation in this design                                                                                                                                                                                                                   | Still open                                                        |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| VAPID private key stolen (admin Worker or CI leak)                | Secret of the admin Worker only, set with `wrangler secret`, never in code, logs, docs or fixtures; empty pushes mean a thief can only send "a new request is waiting"; key rotation step in the runbook (all subscriptions must re-opt-in) | Rotation drill not yet run; owner holds the key backup            |
| Push endpoints leak (database read, log, error)                   | Treated as credentials: never logged or returned, never shown on admin pages, deleted on opt-out, status change and sweep; log scrubbing test                                                                                               | D1 is not encrypted with our own key; Cloudflare is the processor |
| Forged or spam pushes to a partner                                | Only the admin Worker holds the key; empty payload; per-partner hourly and daily caps; per-admin nudge limit; admin Worker behind Access with CSRF and audit                                                                                | Compromised admin account can still send up to the caps           |
| Notification reveals who is a partner on a shared or locked phone | Generic text, no ghat, kind or name; title is the app name only; opt-in is explicit and reversible                                                                                                                                          | Whether the app name itself is sensitive for some people          |
| Push content used for phishing or links                           | No payload at all; the click always opens the app's own Partners screen; no URL parameters                                                                                                                                                  | —                                                                 |
| Tracking of partners through the push service                     | No location, device model, IP or user-agent stored; subscription tied to pseudonym only; never joined to groups or positions                                                                                                                | Google, Apple and Mozilla see that the device receives pushes     |
| Cross-border processing by push services                          | Disclosed in the partner notice; opt-in separate from applying; refusing costs nothing                                                                                                                                                      | Counsel view on transfer wording (OQ-048)                         |
| Pushes sent after a partner is removed                            | Subscription deleted in the same step as suspend, reject or erase; send query joins only approved and available partners                                                                                                                    | —                                                                 |
| Delay or failure harms someone who relied on it                   | Never promised or shown as delivered; inbox is the record; admin sees sent and failed counts; platform limits documented to partners                                                                                                        | Real-phone delivery times unmeasured                              |
| Nudge flood exhausts the Workers request limit                    | 40-subscription cap per nudge on the free plan; remaining partners see the inbox; cap is configuration                                                                                                                                      | OQ-028 (paid plan) decides the final cap                          |
| Service worker abused to cache personal data                      | Push handlers make no requests and cache nothing; existing allow-list and "no authenticated response cached" rule stay; guard test on `sw.js`                                                                                               | Same-origin script compromise remains a trust risk                |
| Location appears through this feature                             | None collected; no coordinate field in the new table or any log call; location guard test stays in force                                                                                                                                    | —                                                                 |
| Minors receive notifications                                      | Partners are adults only (18+ tick, OQ-046); push is available only to approved partners                                                                                                                                                    | —                                                                 |

## Consequences

- New migration 0010 (expand-only): table `partner_push` (pseudonym, endpoint, keys, created, last success) and `consent_ledger.purpose_id` gains `partner_push` (table rebuild keeping rows and the append-only trigger, as in 0007). Applied to staging D1 by hand before the push, as for earlier migrations.
- New secrets and variables, none created yet: `VAPID_PRIVATE_KEY` (admin Worker secret), `VAPID_PUBLIC_KEY` (public variable, served to the app), `VAPID_SUBJECT` (a contact address for push services, an owner decision: a role mailbox is better than a personal address), `FLAG_PARTNER_PUSH`.
- Library choice: write the VAPID signing (ES256 JWT, RFC 8292) with WebCrypto in the Worker; no payload encryption is needed. No new npm package is expected; if one is proposed it goes through the licence and supply-chain checks first.
- `tests/guards`: extended so the admin Worker still touches only partner tables; endpoints never appear in log calls or API responses; `sw.js` push handler makes no `fetch` and no cache write; no coordinate field in `partner_push`.
- Data inventory DI-26, consent register CON-08, OQ-048 added. The partner privacy notice (OQ-029) must describe push before production. Runbook gets a VAPID rotation step and a "disable all push" step (`FLAG_PARTNER_PUSH` off).
- Build order after approval: (1) migration and repository; (2) subscribe and unsubscribe routes with tests; (3) service worker handlers; (4) admin send path with caps and counts; (5) Partners screen switch and strings in en, te, hi; (6) real-phone check on Android and iPhone in staging; (7) notice and runbook updates.
